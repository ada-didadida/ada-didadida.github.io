当你在 [Stack Overflow](http://stackoverflow.com) 的问题标题里看到“随机”这个词时，几乎可以断定它和无数类似的问题是同根同源的。本文就来探讨一下，为什么随机性会引发这么多问题，以及该怎么应对。<!--more-->

## 问题

Stack Overflow（或者新闻组、邮件列表之类的地方）上的问题通常是这样的：

> 我用 `Random.Next` 生成随机数，但它总是给我同一个数字。每次运行之间会变，但每次运行里它都会把同一个数字生成很多遍。

这是由下面这样的代码造成的：

```C#
// Bad code! Do not use!
for (int i = 0; i < 100; i++)
{
    Console.WriteLine(GenerateDigit());
}
...
static int GenerateDigit()
{
    Random rng = new Random();
    // Assume there'd be more logic here really
    return rng.Next(10);
}
```

那么，问题出在哪儿？

## 解释

`Random` 类并不是真正的随机数生成器。它是一个*伪随机*数生成器。任何一个 `Random` 实例都持有一定量的状态，当你调用 `Next`（或 `NextDouble`、`NextBytes`）时，它会用这个状态返回给你一些*看起来*是随机的数据，同时相应地改变自己的内部状态，这样下次调用时你又会得到一个看似随机的数。

*这一切都是确定性的。* 如果你用一个相同的初始状态（可以通过*种子*提供）来初始化一个 `Random` 实例，并对它做同样的方法调用序列，你就会得到相同的结果。

那么我们的示例代码错在哪儿？我们在循环的每次迭代里都用了新的 `Random` 实例。`Random` 的无参构造函数用当前日期和时间作为种子——而在内部计时器发现当前日期时间已经改变之前，你通常能执行相当多的代码。所以我们一次又一次地用了同一个种子——于是也一次又一次地得到相同的结果。

## 我们能做些什么？

这个问题有很多种解法——其中一些比另一些好。我们先把其中一个排除掉，因为它和其余的都不一样。

### 使用加密随机数生成器

.NET 里有个 `RandomNumberGenerator` 类，它是所有加密随机数生成器都应该派生自的抽象类。框架本身就附带了一个这样的派生类：`RNGCryptoServiceProvider`。加密随机数生成器的思路是：即便它可能仍然是伪随机的，它也会极力做到不可预测。内置实现会采集若干种熵源，它们实际上代表着你电脑里的各种“噪声”，非常难以预测。它可能不只把这些噪声用来计算种子，在生成后续数字时也会用到，因此即便你知道当前状态，也不足以预测接下来的结果（或者已经生成过的结果）。不过这取决于具体实现。Windows 还能利用专门的硬件随机源（比如一块监视放射性同位素衰变的硬件），让随机数生成器更加安全。

把它和 `Random` 对比一下。如果你看到（比如说）10 次调用 `Random.Next(100)` 的结果，并且愿意投入相当的算力，你很可能就能推算出初始种子，从而预测*下一个*结果……甚至可能还能推算出*之前*的结果。如果这些随机数被用于安全或金融目的，那简直是灾难。加密随机数生成器一般比 `Random` 慢，但在提供难以预测且相互独立的数字这一点上做得好得多。

很多情况下，随机数生成器的性能并不是问题——问题在于有没有一个好用的 API。`RandomNumberGenerator` 基本上就是为生成随机字节而设计的——仅此而已。对比一下 `Random` 的 API，它让你可以要一个随机整数、一个随机 `double`、或者一组随机字节。我通常需要的是一个范围内的整数——而要从一个随机字节数组里可靠、均匀地得到它，可没那么简单。远非不可能，但至少你多半会想在 `RandomNumberGenerator` 之上再包一个适配器类。很多情况下，`Random` 的伪随机性是可以接受的——只要你能避开前面说的那些坑。我们来看看怎么做。

### 反复使用同一个 `Random` 实例

修复“大量重复数字”的核心，就是反复使用同一个 `Random` 实例。这听起来挺简单……比如我们可以把原来的代码改成这样：

```C#
// Somewhat better code...
Random rng = new Random();
for (int i = 0; i < 100; i++)
{
    Console.WriteLine(GenerateDigit(rng));
}
...
static int GenerateDigit(Random rng)
{
    // Assume there'd be more logic here really
    return rng.Next(10);
}
```

现在我们的循环会打印出不同的数字了……但事情还没完。如果你在短时间内多次调用这段代码会怎样？我们仍然可能创建两个种子相同的 `Random` 实例……虽然每次生成的数字串里包含的数字各不相同，但我们很容易遇到两次得到同一串数字的情况。

有两种避免这个问题的办法。一种是用一个静态字段维护一个 `Random` 单实例，所有地方都用它。或者，我们当然也可以把实例化往更高层推——一直推到程序顶层，那里只实例化一个 `Random`，然后往下到处传。这是个好主意（而且很好地表达了依赖关系），但它并不能完全解决问题……至少，如果你的代码用到多个线程，就可能出问题。

## 线程安全

`Random` 不是线程安全的。这真让人头疼，因为我们理想上希望整个程序里到处都用同一个实例。但不行，如果你从多个线程同时使用同一个实例，很可能最终内部状态变成全零，这时候这个实例就没用了。

在我看来最好的做法仍然是只用一个实例，但*同时*配一把锁，每个调用方在用这个随机数生成器时都必须记得去获取它。可以用一个替你加锁的包装类来简化这件事，但在重度多线程的系统中，你仍然可能把大量时间浪费在等锁上。

我*曾经*推荐过一种做法：每个线程用自己的随机数生成器，用线程局部变量实现。可惜，至少对 `System.Random` 来说，这会导致生成的数字出现“模式”——而你绝对不想看到模式。最简单的做法是维护一个主种子（基于时间生成一次），然后每次需要一个新随机数生成器时就把它递增。稍微好一点的做法是用一个主随机数生成器来生成种子——但这两者都算不上特别有效。我猜如果换一个更好的随机数生成器，后一种做法是可行的，但如果你用的是 `System.Random`，那还不如干脆认了加锁的代价。这个问题涉及的具体表现，可以看[这个 Stack Overflow 问题](http://stackoverflow.com/questions/36376888)。

## 接口设计上的问题

还有一个问题：这样仍然不够安全。如前所述，`RandomNumberGenerator` 里有个更安全的版本，最常用的派生类是 [`RNGCryptoServiceProvider`](http://msdn.microsoft.com/en-us/library/system.security.cryptography.rngcryptoserviceprovider.aspx)。但它的 API 在常见场景下是真的难用。

如果框架的设计者能把“随机源”这个概念和“我想用简单的方式得到一个随机值”这个概念分开，那该多好。那样我们就可以用一个简单的 API，背后接安全或不安全的随机源，取决于我们的需求。可惜，这事没能成真。也许未来某个版本会……也许会有第三方做出一个适配器。（可惜这超出我的能力范围了……把这种事真正做对是极其困难的。）你*几乎*可以通过从 `Random` 派生并重写 `Sample` 和 `NextBytes` 来蒙混过关……但它们到底该怎么工作并不清楚，而且连 `Sample` 都可能很棘手。也许下次吧……
