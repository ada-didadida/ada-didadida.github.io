区间与边角情况

发表于2026-11-17|更新于2026-11-17|C#翻译
|总字数:3841|阅读时长:15 分钟|浏览量:

《C# in Depth》第一版里有一个抽象的泛型 Range 类，它用一个虚方法在区间的各个元素之间步进。遗憾的是，有些边角情况处理起来相当别扭。本文与其说是在设计一个完美的区间类，不如说是在讨论需要考虑哪些因素。我的 MiscUtil 库里有一个类处理了其中相当多的部分，当然也还有改进空间。我之前写过一篇博客谈这个话题，但我觉得它值得再聊一次。

大范围界定

先来比较笼统地定义一下我们希望能做到什么：

  • 为任何合适的类型创建一种区间的表示
  • 用某个自定义的步进函数遍历这些值

所以，范围内的东西并不多……不过魔鬼藏在细节里。我们明确地把一些东西排除在范围之外。我不打算：

  • 考虑两个区间的相等性
  • 考虑两个区间的交集、并集等等
  • 把区间当成一组离散值（比如“0 到 100 之间的偶数”）
  • 处理那些在区间内乱跳的步进函数（也就是说，它应该始终递增，或者始终递减）——后面我们会看到为什么

有了这么宽的界定，我们大概可以开始考虑一些细节了。

细节

首先想想哪些类型是适用的。我们希望它是泛型的，并且希望能够比较任意两个值。我们可以通过约束 T 实现 IComparable<T> 来做到——但那样就没法使用那些在泛型出现之前设计、并且没有更新实现新接口的类型了。而且，只用默认比较在之后可能会有些局限……特别是我心里已经有个想法：反转一个区间的一种办法，就是把它的最小值和最大值对调，同时把比较的方向也反过来。

说实话，我想不出有什么场合真的需要创建一个没有常规比较方式的区间——但我很确信我们确实需要能用自定义的比较。现在我们又有一个选择：这个比较是用 IComparer<T> 还是 Comparison<T> 来表达？两者等价——但 IComparer<T> 大概更常见，所以就用它。这也意味着我们可以直接用 Comparer<T>.Default 来做自然比较，不用再折腾别的。如果调用方想用 Comparison<T>，写个适配器类很容易（MiscUtil 里就有一个）。

回到约束的决策上，这是个有意思的设计取舍：是可能把调用方约束得太死、让他们在确实有正当理由为非自然可比较类型创建区间时感到憋屈，还是不约束、冒着类型被不当使用的风险？权衡下来，虽然我喜欢把 API 使用者推向合适的选择，但在这里我更倾向于不加约束。对那些怪异情形来说，代价太高了。

好，我们知道会有一个比较器——而且很可能会有上下边界。但这引出了更多问题：

  • 边界应该是包含的还是排除的（也就是区间是闭的还是开的）？
  • 我们总是需要两个边界吗，还是可以有只有下界或只有上界的区间？（甚至两者都没有，表示该类型所有值覆盖的区间。）
  • 遍历一个下界为开的区间是什么意思？
  • 遍历一个没有下界的区间是什么意思？

因为我想让这件事保持适度简单，所以暂时只做有限区间——也就是总是有上下两个边界。默认下界包含（闭）、上界排除（开），但会有可选的构造函数参数允许其他可能。同样，我默认使用该类型的默认比较器，但允许指定自定义比较。这里我用 null 作为比较器的默认值——诚然，如果有人不小心传了个 null 引用进来，这可能掩盖一个 bug，但除此之外相当简洁。（一点意外之喜是，如果你想显式使用默认比较器，可以传 default(IComparer<T>)——当然，那就是 null。）“从开边界开始迭代”的问题我们后面再说。

动手之前最后一个设计要点：我们要把这个类型做成不可变的。当然，如果元素类型本身可变，我们也无能为力，但大多数合理的区间元素类型本来就是天然不可变的。

遍历

回到涉及的设计问题。我觉得相当清楚的一点是，我们需要某种步进函数，把现有的值变成下一个值。然后就剩两个问题：第一个值用什么，以及什么时候停？

从哪里开始？

下界包含的情况下，第一个问题好回答：直接从下界开始。下界排除时就比较难定义了。假设我们在用一个区间 (0, 50)（两端都排除），每次步进 5。第一个值应该是 1（区间里最小的值）还是 5（从 0 开始并跳过第一个值的结果）？在很多情况下，找出一个确实被包含在区间里的最小值很难，在另一些情况下则根本不可能，尤其是有自定义比较器的时候。比如，我的单元测试里有一个自定义的 IComparer<int>，它只比较任意两个整数的最后两位。于是你可以有一个区间 (41, 37)，它“包含” 23、12 和 44，但不包含 38。这个区间里的最小值是什么？

接下来是第二个问题……

什么时候停？

这里同样有多个选项。最重要的一点是先排除一种有毛病的做法：我们不应该一直迭代下去，直到拿到的值不在区间里为止。那样的话，遍历一个 0 到 255（包含）的 Range<byte> 就不可能了——而那是一个完全合理的可遍历区间。有这些选项：

  • 用两个步进函数，一个用来问是否还有下一个值，一个用来求出那个值是什么。
  • 用一个步进函数，但让它一次返回这两项信息。这就引出几个子选项：
    • 用 Func<Tuple<bool, T>> 一起返回两个值
    • 用一个带 out 参数的委托（呃）
    • 试着用 null 作为“没有更多值”的结果；如果我们把 T 约束为值类型，这倒不难，但不是个好方案
  • 要么在下一个值超出区间时停止，要么在它等于或小于前一个值时停止，从而防止回绕

我觉得最后一个选项最干净——而且它要求调用方做的工作最少，只需要给出一个简单的“在上一个值上加 n”这样的步进函数。它稍微不够灵活，因为我们不能有在区间内乱跳的步进函数，但它用更简单的方式覆盖了最常见的情形。实现容易，用起来也容易。

小结

我们这里没写多少代码，但最终得到了一个有用的小类。一开始就把这个类的范围界定清楚很重要——早期不同的决策会彻底改变实现——但同样重要的是考虑到那些边角情况，比如回绕、不改变原值的步进函数，以及返回 int.MinValue 的比较。这里所有代码都可以下载，其中包括一些简短的单元测试来检验它。
