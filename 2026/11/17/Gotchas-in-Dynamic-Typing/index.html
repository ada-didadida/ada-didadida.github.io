动态类型中的陷阱

发表于2026-11-17|更新于2026-11-17|C#翻译
|总字数:2288|阅读时长:9 分钟|浏览量:

C# 的 dynamic 支持很棒，但有些刁钻的地方值得了解，因为它们很容易把你绊一跤。如果你自己也遇到了，请写信告诉我，我会把它们加进这个清单。

显式接口实现

要记住：当执行时编译器处理一个动态表达式时，它考虑的是对象的实际类型，而不是你原本可能掌握的其他信息。（实际上还要稍微复杂一点，因为对象可能是调用代码根本不了解的类型。编译器会算出“最佳可访问类型”并据此行事，但大多数时候你不需要操心这一点。）它的行为就像你声明了一个该类型的变量，然后走正常的步骤去判断该走哪条执行路径。

这通常没问题，但它和显式接口实现配合得不好。如果你还记得，显式接口实现只允许你通过接口类型的表达式来调用被实现的成员。假定实际实现类型是可访问的，这就意味着执行时编译器找不到相关成员。下面是书里那个例子，我稍微改了一下：

最后，记住：当用作实参的动态表达式的值为 null 时，重载解析大致等价于直接传入字面量 null 作为实参……编译器没有其他类型信息可以帮它判断你想要什么，所以你很容易就掉进歧义里。

匿名类型

你可以在动态类型里使用匿名类型，事实上这在 ASP.NET MVC 里相当常见。然而，你需要知道：用来实现匿名类型的那些“真正的”类型（由编译器生成）是 internal 的。动态类型遵守正常的访问控制规则，所以如果你想从另一个程序集动态地使用某个匿名类型的实例，就需要用 [InternalsVisibleTo] 把访问权限从包含该类型的程序集授予使用它的程序集。

WCF、IClientChannel 与代理

WCF 用 RealProxy 来实现服务代理。相当令人惊讶的是，RealProxy 确实能和 dynamic 一起工作，只要调用 GetType 能返回正确的类型。WCF 返回的代理同时实现了 IClientChannel 和你正在代理的服务 API 接口——但 GetType 只返回 API 接口。所以如果你试图通过一个动态值去调用 IClientChannel 的任何一个成员，它就会失败。这和显式接口实现类似——就好像代理是以显式方式实现 IClientChannel 的。

小结

这个页面上描述的行为，没有一条应该被称作 C# 编译器（无论是“正常的”那个还是动态执行所用的内嵌版本）的 bug。它们仅仅是你可能不会去想的一些事情。使用动态类型时你绝对需要小心——它很强大，但并不总是完全按你预期的方式工作。
