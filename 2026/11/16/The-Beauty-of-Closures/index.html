闭包之美

发表于2026-11-16|更新于2026-11-17|C#翻译
|总字数:5249|阅读时长:21 分钟|浏览量:

Java 7 还没发布的时候，我想写一篇博客，聊聊当时围绕 Java 7 闭包的各种提案。可是真动手写才发现，如果不先介绍一下闭包，这篇文章简直无从下笔。越写下去，这个引言变得越长，我担心读者还没读到 Java 7 那部分就跑光了。所以我想，不如干脆单独写一篇专门讲闭包的文章。至于那篇 Java 7 的博客——如你所见，最后也没写成。

大多数讲闭包的文章都是用函数式语言来写的，因为函数式语言对闭包的支持往往最好。但这也恰恰是为什么值得写一篇讲闭包在更传统的面向对象语言里长什么样的文章——如果你本来就在用函数式语言，那你多半早就知道闭包了。本文讨论的是 C#（1、2、3 版）和 Java（7 之前的版本）。

什么是闭包？

简单地说，闭包让你可以把某段行为封装起来，像传递其他对象一样把它传来传去，同时它仍然能访问自己被声明时所处的上下文。这样一来，你就可以把控制结构、逻辑运算符等等，与它们具体如何被使用的细节分离开来。能够访问原始上下文，正是闭包区别于普通对象的地方——尽管闭包的实现通常也是用普通对象加上编译器的一点小把戏来做到的。

用一个例子来展示闭包的诸多好处（以及它的实现方式）是最容易的。本文接下来大部分内容都会用同一个例子。我会用 Java 和 C#（不同版本）来展示代码，说明不同的做法。所有代码都可以下载，方便你自己动手改。

示例场景：过滤列表

按某种条件过滤一个列表，是相当常见的需求。直接“内联”写也很容易：新建一个列表，遍历原列表，把符合条件的元素加进去。只需要几行代码，但把这段逻辑集中藏在一个地方仍然更好。真正困难的地方在于，如何把“该包含哪些元素”这件事封装起来。这就是闭包登场的地方。

虽然我在描述里用了“过滤”这个词，但它在“往新列表里筛进”和“从原列表里筛掉”之间是有点含糊的。比如一个“偶数过滤器”，到底是保留偶数还是剔除偶数？我们换一个术语——谓词（predicate）。谓词就是“能匹配或不能匹配某个给定元素”的东西。我们的例子会生成一个新列表，其中包含原列表中所有匹配给定谓词的元素。

在 C# 中，表示谓词最自然的方式是委托，事实上 .NET 2.0 里就有一个 Predicate<T> 类型。（题外话：不知为何 LINQ 更偏爱 Func<T,bool>；我觉得它描述性更差，不太明白为什么。这两个在功能上是等价的。）Java 里没有委托这种东西，所以我们就用一个只有一个方法的接口。当然，在 C# 里也可以用接口，但那样会明显更麻烦，而且没法用匿名方法和 lambda 表达式——而恰恰是这些特性在 C# 里实现了闭包。下面是这个接口/委托的定义，供参考：

既然看到了 C# 对捕获变量变化的反应，那 Java 里会怎样？答案很简单：你没法改变被捕获变量的值。它必须是 final 的，所以这个问题根本不存在。不过，假如你能够改变这个变量的值，你会发现在谓词那边不会有任何反应。被捕获变量的值在谓词创建时就被复制了，存放在匿名类的实例里。对于引用类型的变量，别忘了变量里存的只是那个引用，而不是对象当前的状态。比如你捕获了一个 StringBuilder，然后往里面追加内容，这些变化在匿名类里是能看到的。

这有什么大不了的？

在这个例子里，我们只看到了闭包带来的一点点好处。没错，我们把控制结构那一侧和过滤本身所需的逻辑分开了，但光凭这一点，代码并没有变得那么简单。这是很常见的情形——一个新特性放在过于简单的例子里，往往显得没那么惊艳。然而闭包常常带来的好处是可组合性。如果这话听起来有点勉强，我同意——而这本身就说明了一些问题。等你熟悉了闭包、甚至有点上瘾之后，这层联系会显得显而易见。在那之前，它看着就很晦涩。

闭包并不天然提供可组合性。它们做的只是让实现委托变得更容易（或者说让实现单方法接口更容易——为简单起见我就用“委托”这个词了）。在没有闭包支持的情况下，写个小循环比“调用另一个方法去循环、并给它传一个委托来完成其中一部分逻辑”要容易。即便有了“在现有类上加个方法”这种委托支持，你仍然会失去逻辑的局部性，而且往往需要比轻易能提供的更多的上下文信息。

所以，闭包让创建委托变得更简单。这意味着设计使用委托的 API 变得更值得。（我不认为这只是巧合：在 .NET 1.1 里，委托几乎只被用来启动线程和处理事件。）一旦你开始用委托的方式思考，组合它们的方法就变得显而易见了。比如，创建一个接收另外两个谓词、表示二者逻辑与或逻辑或（当然也可以是其他布尔运算）的 Predicate<T>，是件轻而易举的事。

另一种组合方式，是把一个委托的结果喂给另一个委托，或者把一个委托柯里化，产生一个新的委托。一旦你开始把逻辑当成另一种数据来看待，各种可能性就都出现了。

组合的用途还不止于此——整个 LINQ 都建立在它之上。我们用列表做的那个过滤，只是“一串数据变换成另一串数据”的一个例子。其他操作还包括排序、分组、与另一个序列合并、投影。以往把这些操作一个个手写出来并不算太痛苦，但当你的“数据管道”里包含的不止几次变换时，复杂度很快就会累积起来。此外，借助 LINQ to Objects 提供的延迟执行和数据流式处理，相比“跑完一个变换再跑下一个”的直白实现，你在内存开销上要省得多。复杂度之所以被消解，并不是因为单个变换本身有多聪明——而是因为你能用闭包就地把一小段逻辑写在它该在的位置，还能用一个设计良好的 API 把各种操作组合起来。

小结

闭包一开始是有点让人提不太起劲的。没错，它们让你能相当简单地实现一个接口或创建一个委托实例（取决于语言）。它们的威力只有在你把它们和那些善用闭包的库一起使用时才显现出来——那些库让你能在恰好的位置表达自定义的行为。当这些库还允许你以自然的方式把几个简单步骤组合起来、实现相当复杂的行为时，你得到的东西的复杂度就只有各部分复杂度之和——而不是各部分复杂度的乘积。虽然我不太认同“可组合性是战胜复杂性的银弹”这种说法，但它确实是一项强大的技术，而且因为有闭包，它能适用的场景多了很多。

lambda 表达式的一个关键特性是简洁。把前面那段 Java 代码和 C# 代码放在一起比较，Java 显得极其笨重。这正是 Java 闭包的各种提案想要解决的问题之一。关于这些不同的提案，我会在不久之后的一篇博客里谈谈我的看法。
